## 三、做得好的地方（不是客套，是可复用的经验）

5. **测试密度高且快**：426 个用例覆盖 `tick()`，15.7 秒跑完——这是敢改代码的前提，别丢。
6. **密钥纪律**：`.env` / `.env.*` / `config/` 全部 gitignore，仓库里只有 `.env.example`（实测 `git ls-files` 无泄漏）。

## 四、风险清单（按「会不会真丢钱」排序）

### R1 — MT5 调用没有全局锁，4 条线程共享一个终端 session【高｜推断】

- `live/journal.py:47` 有 `_lock`，但**只在 `collect()`（735 行）里用**。
- `_ensure()`（196 行）的 `if _connected: return` 是无锁双检，两个线程可同时 `mt5.initialize()`。
- `live/autotrade.py:3262 _quote()` 直接 `journal._mt5().symbol_info_tick()`，**不入任何锁**。
- 并发来源：worker（每 tick 4 次 MT5 读）+ HTTP handler（`summary()` 里 `_quote`，面板 1.5 秒一次）+ live-recorder（300 秒）+ `_wait_next` 的 guard 快查（2~5 秒一次）。
- 后果：争用时 `symbol_info_tick` 可能返回 `None` → `_quote` 返回 `None` → tick 走「拿不到报价」分支、面板浮盈显示 `—`；极端情况止损判定的报价是空的。
- 现状：**未复现**，属代码层面可确认的结构缺陷。`collect` 的锁给了「已经保护好了」的错觉，实际最常用的报价路径在外面。

### R2 — `tick()` 636 行 / 26 个 return / 60 个分支 / 0 个 try【高｜实测 AST】

- 全文件 34 处 `save_state(state, ...)`、25 处 `append_log(row, ...)`，其中 tick 体内 24 / 21。
- 每个分支都是手写「`append_log(row)` + `save_state(state)` + `return row`」三连。
- 风险不是性能，是**漏写**：新增一个跳过分支忘记 `save_state`，就是「面板显示空仓、实际持仓」，或者「running 掉了但线程还在跑」。这类 bug 只有对账时才发现，而账是钱。
- 另：tick 无 try，全靠 `Worker._loop` 兜底 → 中途抛异常时，已 `append_log` 未 `save_state`，落盘状态与流水不一致。

### R3 — HTTP 层 1,037 行零单测【中高｜实测】

- `do_GET` 390 行 / 21 个路径分支；`do_POST` 622 行。
- `tests/` 里 `Handler` 出现 **0 次**。唯一覆盖是 `tools/smoke_dashboard.js`（Node 假 DOM），它测前端脚本，不测路由与 `confirm` 校验。
- 而 `confirm=true` 是「会不会误下单」的唯一闸门，目前没有任何自动化断言守着。

### R4 — 静默除错 20 处，且价格兜底返回「合法但错误」的值【中｜实测】

`live/` 与 `tools/` 共 118 处 `except Exception`，其中 20 处直接 `return 默认值` / `pass`。典型：

- `_point()` → 失败返回 `0.001`
- `_digits()` → 失败返回 `3`
- `_spread_cost()` → 失败返回 `0.0`

点值错 → `_sl_price_for` 的止损价错；点差成本返回 0 → 成本闸门失效。这些不是崩溃，是**安静地算错**。`# noqa: BLE001` 说明是有意识的，但缺少「降级了」的痕迹（没有日志、没有状态位）。

### R5 — 前端 217 KB 单文件【中｜实测】

5,493 行、190 个内联函数、52 KB 内联样式。改一个卡片要全文搜 ID；diff 上百行，review 等于没 review。`smoke_dashboard.js` 靠正则从 HTML 抠内联脚本，拆文件要同步改它。

### R6 — 零 CI、零 lint、零类型检查【中｜实测：无 `.github/`】

795 个测试只有人记得跑才跑。发版流程（bump → build → release）是手工三步，历史上已经踩过「忘 push 导致 tag 打错」的坑——这正是 CI 该拦的那类错误。

### R7 — 遗留模块的维护税【低】

`portfolio/`（1 处引用）、`execution/`（2 处）、`strategies/`（2 处）在实盘链路里基本不在关键路径上。不危险，但读代码的人要花时间判断「这条到底走不走」，且 `_point/_spread_cost` 反而是从 `backtest.symbols` 借来的——**实盘的价格常量依赖回测模块**，这是个隐性耦合。

## 五、性能：当前不是瓶颈，别优化错地方（实测）

| 路径 | 实测耗时 | 每 tick 次数 | 结论 |
|---|---|---|---|
| `save_state`（1.9 KB，indent=2） | 4.47 ms | ≤24（最坏 107 ms） | 占 60 s 的 0.18%，可忽略 |
| `read_log` 全量（65 行） | 1.88 ms | 面板 summary 每次轮询 1 次 | 当前无感 |
| `lesson_clusters`（43 条教训） | 1.24 ms | 2（进场+出场提示词） | 可忽略 |

**真正的耗时与瓶颈在三处，都不在这张表里：**

1. **LLM 往返 1~3 秒**，决定 `interval_sec=60` 的实际节奏——这才是主成本（时间与钱）。
2. **面板 1.5 秒轮询 × 每次一次 MT5 报价**（`summary()` → `_quote`，为算持仓浮盈）。它不是 CPU 瓶颈，是 **R1 的争用源**：一次页面开着就等于给 MT5 加了 0.67 QPS 的并发读。
3. **随数据量线性退化的点**（现在 65 行流水、43 条教训，还早）：
   - `read_log` 是 `read_text()` 整文件读入再 split，`limit=5000` 只截尾部、不省 IO；
   - `lesson_rows()` 每次全量重建桶；
   - `save_state` 每次写全量 state（含 `cfg`、`pending_reviews`）。

   按每天 ~1,400 行流水估算，一年约 50 万行、~200 MB —— 那时 `read_log` 会到秒级。**现在不用动，但要知道 cliff 在哪。**

## 六、改进建议（按优先级）

### P0 — 会碰到钱/账的，先做

**P0-1 给 MT5 加全局调用锁（R1）**
- 改哪：`live/journal.py` 新增 `mt5_call(fn, *a, **kw)`（`threading.RLock`），`_ensure` 的双检入锁；`live/autotrade.py` 的 `_quote/_bars/_positions/fetch_ticks` 与 `journal` 的 5 处直调全部改为经此入口。
- 为什么：4 线程一个 session，`collect` 的锁只保护自己。这是「偶发拿不到报价」最可能的解释。
- 验证：单测起 20 线程并发 `_quote`，断言 100% 非 `None`（用 `_stubs.py` 的假 MT5 加 1 ms 延迟放大争用）。

**P0-2 tick 落盘收敛为单一出口（R2）**
- 改哪：`live/autotrade.py` 引 `_finish(state, row, login)`；tick 内 21 处三连改成 `return _finish(...)`，并把 `tick()` 整体包一层 `try/except` → 异常也走 `_finish` 落一次带 `kind="error"` 的行。
- 为什么：26 个 return 手写配对，漏一处就是账实不符；现在是靠人记住。
- 验证：断言「tick 返回后 state 必被写过」——monkeypatch `save_state` 计数，跑现有 426 个 tick 用例，全部 ≥1。

**P0-3 价格兜底不许静默（R4）**
- 改哪：`_point/_digits/_spread_cost` 失败时 `append_log({"kind":"degrade", ...})` 并让 `feature_snapshot` 带一个 `degraded` 标记；`_spread_cost` 拿不到就返回 `None`，成本闸门按「未知」处理而不是「0 成本」。
- 为什么：0.0 的点差成本会让 `min_edge` 变成永远放行。

### P1 — 可维护性，改完能省未来的时间

**P1-1 拆 tick（R2）**：按「空仓进 / 持仓出」拆 `_tick_flat()` / `_tick_holding()`，`tick()` 只留前置闸门 + 分发。目标各 <200 行。理由：60 个分支的巨型函数无法 review，也无法单测到分支粒度。

**P1-2 端点表驱动（R3）**：`do_GET/do_POST` 的 21+ 分支改成 `ROUTES = {"/api/state": _h_state, ...}` + 一个统一包装（异常 → 500 JSON，缺 confirm → 400）。Handler 从 1,037 行降到 ~150 行。

**P1-3 补 HTTP 单测（R3）**：起 server 用 0 端口，覆盖 4 条：`/api/state` 正常、`/api/autotrade` 正常、付费端点缺 `confirm` → 400、未知路径 → 404。理由：这是唯一自动化守着「误下单」闸门的地方。

**P1-4 前端三拆（R5）**：`dashboard_template.html` → `.html` + `app.css` + `app.js`，dashboard 用静态路由服务；同步改 `smoke_dashboard.js` 的抠取逻辑与 `.gitignore` 的 `!tools/*.html` 例外规则。理由：这是目前最影响「敢不敢改 UI」的因素。

### P2 — 工程流程

**P2-1 加 CI（R6）**：GitHub Actions `windows-latest` + `python -m unittest discover -s tests`，15.7 秒实测完全跑得动。加一步「tag 必须指向 main 尖端」检查，把 v1.5.7 那个坑制度化拦住。理由：795 个测试的价值取决于它是否**自动**跑。
